# Задание для Codex: акты выдачи оборудования

Дата: 29.09.2026. Статус: согласованы сценарий и макет; реализация приложения ещё не выполнена. Реальный шаблон DOCX и рабочая выгрузка будут предоставлены владельцем отдельно.

## 1. Что нужно сделать

Реализуй небольшое внутреннее веб-приложение для формирования актов выдачи оборудования по готовому шаблону Word. Основной сценарий: найти конкретное устройство в базе → выбрать его → автоматически показать реквизиты → добавить в акт → указать получателя → скачать заполненный DOCX.

Рядом находится `interface-reference.html` — согласованный интерактивный макет с вымышленными данными. Сохрани его компоновку, названия основных действий и логику выбора. Это визуальный ориентир: хранение данных в JavaScript в нём демонстрационное. В приложении источником данных должен стать PostgreSQL через Go-бэкенд. Проверка макета в настоящем браузере в этой среде не выполнена; перед переносом проверь взаимодействия и адаптивную вёрстку.

Начни с чтения действующих AGENTS.md и файлов проекта. Если код уже существует, доработай его без удаления пользовательских изменений. В новом проекте создай минимальную структуру. Не меняй выбранный стек и не добавляй инфраструктуру без конкретной необходимости.

Не используй плавающий `latest`. PostgreSQL 18 может служить исходной поддерживаемой основной версией; конкретный образ проверь при реализации.

## 3. Границы первой версии

В первой версии нужны поиск, ручное добавление оборудования, составление одного акта с несколькими устройствами, импорт согласованного CSV и финальное заполнение предоставленного DOCX.

Текущий ответственный и получатель акта — разные значения. Формирование и скачивание документа не меняют ответственного в базе и не проводят передачу в 1С. Удаление строки из акта не удаляет устройство из базы.

Принятые для первой версии допущения:

- Одна строка базы — один физический экземпляр; количество в строке акта всегда 1.
- Первый набор оборудования относится к одному контуру учёта, в котором инвентарный номер уникален. Перед импортом проверь это на выгрузке. Если номера повторяются между организациями, нужно уточнить ключ; объединять такие записи нельзя.
- Получатель и текущий ответственный пока вводятся текстом. Справочник сотрудников не предоставлен.
- Номер акта вводится вручную; автоматическая нумерация и правила её уникальности пока не заданы.
- Черновик составляется в открытой странице. Архив актов, сохранение черновиков между сеансами, электронная подпись, учёт факта выдачи и прямая синхронизация с 1С не входят в первую версию.
- Первый запуск — на компьютере администратора через localhost. Серверное размещение для нескольких сотрудников потребует отдельного решения о доступе и аутентификации.

Не создавай универсальную систему инвентаризации, SPA, каталог интеграций или отдельный поисковый сервис.

## 4. Интерфейс и поведение

### Данные акта

Поля: номер, дата, получатель. Дата по умолчанию — текущая календарная дата в `Europe/Moscow`, с возможностью изменения. Обязательность дополнительных реквизитов определить по реальному шаблону на последнем этапе.

### Поиск оборудования

Одна строка поиска по типу, модели, инвентарному и серийному номерам. Рядом необязательный фильтр типа: «Все типы», далее фактические типы из базы. Не загружай весь справочник устройств в браузер.

Под строкой показывай результаты: тип, модель, инвентарный номер, серийный номер и текущий ответственный. Для одинаковых моделей обязательно различать экземпляры по номерам. Совпадение в поиске само по себе не означает выбор: пользователь должен нажать на конкретное устройство.

После выбора автоматически показывай все реквизиты карточки, включая дату поступления и стоимость в утверждённом формате. Карточка выбранного устройства в форме акта доступна для чтения. Исправление справочника — отдельная операция, не скрытая часть формирования документа.

Нужны понятные состояния: загрузка, ничего не найдено, ошибка сервера, выбранное устройство, устройство уже добавлено. После смены поисковой строки не оставляй старую выбранную карточку, если её больше нет среди текущих результатов.

### Две разные кнопки

1. **«Новое оборудование»** — открывает форму создания записи: тип, модель, инвентарный номер 1С, серийный номер, дата поступления, текущий ответственный, итоговая стоимость, режим НДС, ставка и сумма НДС. После успешного сохранения запись появляется в поиске и становится выбранной. Она ещё не входит в акт.
2. **«Добавить в акт»** — включает выбранный экземпляр в список оборудования текущего документа. Повторно добавить тот же экземпляр нельзя. Доступна кнопка «Убрать», действующая только на список акта.

Тип можно выбрать из существующих либо ввести новый. Отменённая форма ничего не сохраняет. При ошибке заполненные поля сохраняются, рядом выводится причина. Валидация обязательна на сервере, независимо от браузера.

### Оборудование в акте

Показывай список выбранных экземпляров, их идентификаторы, стоимость и общую сумму. Порядок строк соответствует порядку добавления. Получатель относится ко всему акту. Итог рассчитывается на сервере по данным базы.

Кнопка «Сформировать Word» включается, когда есть позиции, заполнены обязательные реквизиты и подключён проверенный шаблон. До подключения шаблона показывай недоступное действие с кратким пояснением. Не выдавай HTML, пустой файл или самодельный документ за результат заполнения пользовательского шаблона.

Сохрани русский интерфейс, работу с клавиатуры и пригодность для экрана ноутбука. Не добавляй дашборды и показатели, не нужные для составления акта.

## 5. Данные оборудования

Минимальная таблица `assets`:

| Поле | Хранение и правило |
|---|---|
| `id` | Внутренний идентификатор записи, PK |
| `equipment_type` | Текст, обязателен |
| `model` | Текст, обязателен |
| `inventory_number` | Текст, обязателен; уникален в принятом контуре учёта |
| `serial_number` | Текст или NULL; глобальную уникальность не предполагать |
| `received_date` | SQL DATE или NULL |
| `current_holder` | Текст или NULL |
| `price_minor` | BIGINT, итоговая стоимость в копейках, неотрицательная |
| `vat_mode` | `included` или `none` |
| `vat_rate` | Точное десятичное значение ставки, например NUMERIC(5,2); NULL для `none` |
| `vat_minor` | BIGINT, сумма НДС в копейках |
| `created_at`, `updated_at` | TIMESTAMPTZ |

Уникальность инвентарного номера проверяй в БД после согласованной нормализации регистра и пробелов по краям. Исходное написание сохраняй для отображения. Начальные нули, дефисы и внутренние символы номеров не удаляй. Разные серийные номера не объединяй на основании сходства текста.

Для типа и модели убирай случайные пробелы по краям; существующий тип с другим регистром используй повторно. Не выдумывай дату или ответственного для пропущенных значений.

Ограничения денег и НДС закрепи в БД и Go: `0 <= vat_minor <= price_minor`; для `none` ставка NULL, сумма НДС 0; для `included` ставка задана. «Без НДС» и «НДС 0%» — разные режимы. Ставку 22% не зашивай как единственно возможную.

## 6. Стоимость и точность

Не используй `float32`/`float64` для денежных расчётов. Суммы из формы и CSV разбирай из десятичной строки в целые копейки с проверкой диапазона. Для JSON денежные значения передавай десятичными строками либо готовым представлением; не допускай потери точности в JavaScript.

Сумму и НДС из учётной выгрузки сохраняй как предоставлены. Не заменяй исходную сумму НДС результатом повторного расчёта по ставке. Несогласованность можно показать пользователю, но нельзя исправлять скрыто.

Утверждённое представление:

```text
27 600 руб. 00 коп., в т. ч. НДС 22% — 4 977 руб. 05 коп.
2 409 руб. 00 коп., без НДС
```

Внутри системы стоимость не хранится одной готовой строкой. Для общего итога складывай суммы позиций. Если шаблон содержит итог по НДС, складывай исходный НДС и группируй по ставкам; смешанным ставкам нельзя приписывать единую ставку. Один форматтер используй для страницы и DOCX.

## 7. Поиск и индексы

Создай расширение `pg_trgm` через миграцию и GIN-индексы `gin_trgm_ops` для полей поиска либо обоснованного составного поискового представления. Обычный индекс для точного инвентарного номера также нужен. SQL должен обращаться к тем же полям/выражениям, которые индексируются.

Основная семантика — поиск подстроки без учёта регистра, например через параметризованный `ILIKE`. Не заменяй её только поиском похожих слов: фрагмент серийного номера должен находить точное вхождение. Символы `%`, `_` и символ экранирования в пользовательском вводе трактуй буквально.

Первые результаты: точное совпадение номера, затем совпадение начала, затем вхождение. Используй стабильную сортировку при равном приоритете. Возвращай не более 20 записей и признак наличия остальных; предлагай уточнить запрос. Пустой запрос не должен выгружать весь справочник.

В браузере сделай задержку около 250 мс, отмену устаревшего запроса и защиту от отображения позднего ответа для предыдущего текста. SQL выполняй с контекстом запроса и ограничением времени.

Короткие запросы из 1–2 символов могут не выигрывать от триграммного индекса. Они должны оставаться ограниченными по результатам и времени; фильтр типа позволяет выбрать короткое название вроде «ПК». Не обещай использование GIN для любого ввода.

После появления репрезентативного набора данных проверь несколько запросов через `EXPLAIN (ANALYZE, BUFFERS)`. На трёх демонстрационных строках последовательное сканирование может быть нормальным выбором планировщика — не отключай его ради красивого отчёта.

## 8. CSV для импорта

Фиксированный контракт: UTF-8, необязательный BOM, разделитель `;`, заголовок обязателен; даты `YYYY-MM-DD`, деньги в рублях с точкой и двумя десятичными знаками. Для разбора использовать `encoding/csv`, не разделение строк вручную.

```csv
equipment_type;model;inventory_number;serial_number;received_date;current_holder;price_rub;vat_mode;vat_rate;vat_rub
Ноутбук;HONOR MagicBook X16;DEMO-0001;DEMO-HN-001;2026-09-01;Склад;27600.00;included;22;4977.05
Монитор;Пример монитора;DEMO-0002;DEMO-MN-002;2026-09-02;Склад;18000.00;none;;0.00
```

Для новых записей обязательны тип, модель, инвентарный номер, стоимость и режим НДС. При `included` обязательны ставка и сумма НДС. Правила пропусков соответствуют схеме БД.

Сначала реализуй проверку файла без записи: соответствие колонок, типы, даты, денежные значения, повторы номеров внутри файла и конфликты с базой. Ошибки показывай с номером CSV-записи и названием поля, не раскрывая всё содержимое строки в логах.

Первая версия импорта только добавляет записи. Повторный импорт идентичных строк пропускает их; тот же инвентарный номер с другими реквизитами является конфликтом. Не обновляй автоматически ответственных и цены, не удаляй записи, отсутствующие в выгрузке.

Запись после успешной проверки — одной транзакцией: либо все новые строки, либо ни одной. Повторно проверь ограничения в самой транзакции; предварительный просмотр не защищает от параллельных изменений. Отчёт: добавлено, пропущено, конфликтов, ошибок.

Для первой версии достаточно отдельной команды `cmd/import-assets` с режимом проверки по умолчанию и явным `--apply` для записи. Не требуется экран импорта. Зафиксируй точные команды в README и добавь один обезличенный пример.

## 9. Генерация DOCX — финальный этап

До получения настоящего шаблона реализуй остальные части полностью. Изолируй генератор в `internal/docgen`, но не создавай фиктивную готовую интеграцию.

При получении шаблона сначала проведи минимальный прогон на его копии: один экземпляр, кириллица, длинное название, стоимость с НДС, символы `&` и `<`, плейсхолдеры в таблице и колонтитулах, если они там есть. Исходник не изменяй.

`go-docx` документирует замену текстовых плейсхолдеров, в том числе разбитых Word на фрагменты. Из этого не следует поддержка повторения строк таблицы. В опубликованном API нет отдельной операции повторения строки. Стандартные разделители — одиночные `{` и `}`; смена разделителей принимает одиночные символы. Реальный синтаксис шаблона, включая возможные двойные скобки, нужно проверить пробным заполнением.

После успешного прогона одного устройства проверь 3 устройства и переход таблицы на следующую страницу. Если фиксированный шаблон не позволяет разместить нужное число строк, покажи конкретное ограничение и минимальный вариант решения для этого шаблона. Не меняй библиотеку или структуру оригинала молча; не разрабатывай универсальный редактор OOXML заранее.

При генерации браузер отправляет реквизиты акта и упорядоченный список ID устройств. Сервер заново читает данные из БД, проверяет наличие и отсутствие повторов, формирует согласованный набор значений и рассчитывает итог. Не доверяй присланной браузером цене или ответственному. Если данные изменились после выбора, покажи изменение до выдачи итогового документа.

Каждая генерация должна иметь независимый экземпляр документа и уникальные временные ресурсы. Проверь параллельные вызовы библиотеки; если её состояние небезопасно для параллельного использования, сериализуй участок генерации в приложении. Не изменяй глобальные разделители во время обработки запросов.

Сначала полностью сформируй и проверь файл, затем отправляй его как DOCX с корректными MIME-типом и `Content-Disposition`. При сбое верни понятную ошибку, без частично скачанного документа. Скачивание не меняет `current_holder`.

Финальная приёмка — открыть результат в Microsoft Word: оформление, таблица, переносы, колонтитулы, итог и отсутствие незаполненных обязательных плейсхолдеров. Структурная проверка XML не заменяет проверку вида документа.

## 10. Простая структура и миграции

Достаточно трёх отдельных точек входа с одной задачей каждая:

- `cmd/server` — обслуживает сайт;
- `cmd/migrate` — применяет SQL-миграции;
- `cmd/import-assets` — проверяет и импортирует согласованный CSV.

Внутренние пакеты разделяй по фактическим задачам: HTTP, работа с БД, форматирование денег, импорт, генерация DOCX. HTML-шаблоны и статические файлы храни отдельно. Не создавай интерфейсы и уровни абстракции без потребителя.

SQL-файлы, например `001_init.sql`, `002_search.sql`, исполняются по порядку. В БД хранится история применённых версий и контрольных сумм. Применённую миграцию не редактировать: изменение оформлять новой. Применение защищено от параллельного запуска; миграция и запись её версии по возможности выполняются в одной транзакции. Для первой схемы выбирай операции, совместимые с транзакцией.

Запуск веб-сервера не должен автоматически изменять схему. При несовместимой версии схемы — понятное сообщение об ошибке. Не добавляй автоматический destructive rollback.

## 11. Docker и эксплуатация первого запуска

Постоянные сервисы Compose: `web` и `db`. Миграции и импорт можно оформить как явно запускаемые одноразовые сервисы/команды. Один Dockerfile со сборкой Go; конечный процесс приложения работает не от root. Node.js для сборки интерфейса не требуется.

Публикуй веб-порт на `127.0.0.1`; порт PostgreSQL наружу не публикуй. Данные PostgreSQL находятся в именованном volume. Проверь корректную точку монтирования для выбранной версии официального образа. Настройки и пароль — через окружение; в Git только `.env.example` без реальных секретов.

Настрой healthcheck PostgreSQL, проверку готовности веб-приложения, таймауты HTTP/SQL и корректное завершение процесса. Ошибка БД должна показываться как ошибка, а не как пустой результат поиска. Состояние схемы проверяется при запуске.

Нужны параметризованные SQL-запросы, экранирование вывода `html/template`, ограничения размера запросов и импортируемых файлов, защита изменяющих запросов от CSRF. В JavaScript пользовательские строки выводи как текст, не через небезопасный `innerHTML`. Успешное создание не должно дублироваться от повторного нажатия; окончательную защиту обеспечивает ограничение БД.

Логи содержат технические события и идентификатор ошибки, но не пароли, содержимое CSV, ФИО, серийники и полные параметры поиска. Реальные выгрузки, рабочие документы, секреты и резервные копии не коммитить. Заполнять тестовую БД только вымышленными данными, по явной команде, не при каждом старте.

README должен содержать проверенные команды: первый запуск; миграции; импорт с проверкой и записью; остановка без удаления данных; резервная копия `pg_dump`; восстановление копии в отдельную тестовую БД. Не объединяй deploy, backup и recovery в универсальный скрипт. Не используй `docker compose down -v` как обычную остановку или исправление неисправности.

Перед миграцией реальной базы — резервная копия и проверяемая точка восстановления. Восстановление сначала испытывается на отдельной БД, без перезаписи рабочей.

## 12. Этапы выполнения и проверка

### Этап A. Один ручной рабочий процесс

Подними Go + PostgreSQL в Compose, создай схему, подключи интерфейс к серверу. Через форму вручную добавь два одинаковых по модели устройства с разными номерами. Найди одно по фрагменту серийника, выбери, проверь реквизиты, добавь в акт. Затем добавь второе и убери первое. После перезапуска приложения обе записи должны остаться в базе.

Запиши фактический результат этого прогона. Только затем переходи к массовому импорту. Если браузер или Docker недоступны, честно укажи непроверенную часть и минимальную проверку для владельца; не выдавай чтение кода за успешный запуск.

### Этап B. Импорт и надёжность поиска

Реализуй CSV по фиксированному контракту. Проверь обычный импорт, повтор идентичного файла, конфликт номера, ошибку в середине файла без частичной записи. На репрезентативных данных проверь поиск подстроки и планы запросов.

### Этап C. Реальный шаблон Word

Подключи предоставленный шаблон после проверки одного и нескольких устройств. Сформируй документ через сайт и выполни визуальную приёмку. Если шаблона пока нет, заверши все доступные работы по A и B и явно зафиксируй единственное оставшееся внешнее условие.

### Проверки, которые действительно нужны

Автотесты должны проверять значимые правила: разбор денег без потери копеек; формат суммы и режимы НДС; ограничения и атомарность импорта; выбор конкретного экземпляра и отсутствие дубликатов в акте; поиск по кириллице и частям номеров с буквальным `%`/`_`; повторное чтение сервером данных перед DOCX. Для интеграции SQL используй тестовую PostgreSQL, не заменяй её SQLite. После подключения генератора добавь проверку корректности DOCX и отсутствия незаполненных обязательных маркеров.

Не пиши тесты, повторяющие вёрстку или детали реализации. Не заявляй о прохождении команд, которые не выполнялись.

## 14. Проверенные исходные сведения

- PostgreSQL: `pg_trgm` поддерживает GIN и поиск `LIKE`/`ILIKE`; шаблоны без извлекаемых триграмм могут приводить к полному сканированию индекса. [Официальная документация](https://www.postgresql.org/docs/current/pgtrgm.html).
- `go-docx`: назначение, фрагментированные плейсхолдеры и разделители описаны в [репозитории](https://github.com/lukasjarosch/go-docx); сигнатуры методов — в [документации пакета](https://pkg.go.dev/github.com/lukasjarosch/go-docx). Способ работы с переменным числом строк является нерешённым вопросом конкретного шаблона, а не подтверждённой возможностью библиотеки.

Это требования к будущей реализации, а не отчёт о уже работающем Go-приложении.
